# fm 0.8.0-beta.0 support: design

Date: 2026-09-21. Status: approved in conversation, pending written review.

## Goal

Bring the inspector onto fm 0.8.0-beta.0 (build 29827611) and use the metadata that build newly
reports. Three things, in the order they depend on each other: the new `read:fileOptions` catalog,
the refreshed step-display catalog (which the fixture must catch up to), and the four step types
this build added.

Scope was chosen deliberately and excludes three further capabilities the build also ships. They
are recorded in "Out of scope" below with what each would cost, because each duplicates an
analysis the inspector already computes offline and each adds a live-query path to a page that is
otherwise read-once.

## What the build changes, as measured

The toolkit's own intake (`gaps/intake.json` at tag `v0.7.0`) records the build as
`0.8.0-beta.0` / `29827611`, checked 2026-09-21. Its surface diff against 0.7.0-29823677: three
new catalogs (`fileOptions`, `text`, `variable`), 18 new ops, four new steps, 292 new keys.

`file-options` in the register moved from 0 to 37 of its 54 rows reported. Of the rest, 4 are
wontfix and 13 are still missing: the four "hide from host's file list" rows (two facts, two
spellings each), the eight saved-page-setup rows, and "file script trigger enabled in Browse mode".

## Prerequisite, already done

The toolkit pin. This took three changes rather than the one it looks like:

1. `v0.7.0` pushed to the toolkit remote. npm resolves a `github:` committish by running
   `git ls-remote` against the remote and never consults a local clone, so the tag and its commit
   `db1327d` were invisible to every other machine. Pointing a pin at an unpushed tag hard-fails
   on an unresolvable rev rather than degrading quietly.
2. The pin in `package.json` bumped `#v0.5.1` → `#v0.7.0`. An exact committish never drifts
   forward — that is what pinning is for — so pushing the tag alone changes nothing about what
   installs.
3. `package-lock.json` re-resolved to `db1327d`. **A plain `npm install` is not enough.** It
   prints `up to date`, rewrites only the lockfile's spec line, and leaves the resolved SHA on the
   old commit — so both manifests claim `v0.7.0` over a `0.5.1` tree, which reads as done and is
   not. Forcing it takes `npm install 'github:wimdecorte/fm-adt-toolkit#v0.7.0'`.

`fm` also moved. The new ADT release installs it at
`~/Library/Application Support/ADT/MCP/fm-cli/fm-cli` — a different directory and a different
binary name (`fm-cli`, not `fm`). No change is needed here: the toolkit's `locateFmCli()` at
`v0.7.0` already probes that path, after `FM_CLI_PATH`, `/usr/local/bin/fm` and
`/opt/homebrew/bin/fm`, and verified against the installed copy it returns
`{version: '0.8.0-beta.0', contract: null}`.

## 1. `read:fileOptions`

### What fm answers

Probed read-only against the reference solution. One op, `{"op":"read:fileOptions"}`, answers with
a single object and **no `items` array**:

```json
{"kind":"fileOptions",
 "minimumVersion":{"value":1208,"version":"12.0"},
 "icon":{"type":"custom","typeId":999,"scale":"fit","hasImage":true},
 "switchToLayout":true,
 "layout":{"name":"File Open","id":11},
 "hideToolbars":false,"useDefaultFields":true,
 "underlineMisspellings":true,"smartQuotes":false,
 "asianLineBreaking":true,"romanLineBreaking":true,
 "dataEntry":"system",
 "login":{"mode":"disabled","hasPassword":false},
 "allowStoredCredentials":true,"requireDevicePasscode":false,
 "showSignInFields":true,"requireAuthorization":"fileAndHost",
 "generateThumbnails":true,"thumbnailStorage":"temporary",
 "triggers":[{"event":"OnFirstWindowOpen","eventId":201,"script":"noop","scriptId":2},
             {"event":"OnWindowTransaction","eventId":209,"script":"noop","scriptId":2,"field":""}]}
```

Two shapes to note. `login` reports `hasPassword` as a boolean and never the password, so the
panel cannot leak a credential even if it renders the block verbatim. `icon` reports `hasImage`
and no image bytes. A trigger may carry a `field` key (`OnWindowTransaction` does).

`read:fileOptions` takes an optional `detail`, which fm's own help describes as "accepted only as
true: this report is at full depth either way". The inspector omits it: sending it buys nothing
and implies a choice that does not exist.

`fileOptions:create` and `fileOptions:delete` exist and are documented refusals — File Options is
not a catalog and a file always has exactly one. Neither is ever sent; the read-only guard would
refuse `fileOptions:update` anyway.

### Read plan

`{op: 'read:fileOptions'}` joins the list batch in `ui/read-plan.js`, one per file. It is not added
to `LIST_CATALOGS`: that constant drives `listOp()`, the catalog-counts table and the per-catalog
slots, none of which fit a single block.

### Model

A per-file slot beside `facts`, not a catalog:

```js
file.fileOptions = { block: null, error: null, ops: [], readAt: null }
```

`facts` already establishes this precedent — file-level, single-valued, no ids, not a catalog.
`model.js`'s `isList()` currently returns true for any `read:*` without an `id`, which would send
this op down the list path and store `result.items ?? []`, i.e. nothing, without erroring. So
`applyBatch` routes `catalogOf(op) === 'fileOptions'` before that test, the way it already routes
`'facts'`, and `createFile` initialises the slot. `catalogCounts` is untouched.

### UI

A File Options panel per file in `ui/tabs/solution.js`, below the facts list, with its own re-read
button. Rendered as a `kv` list grouped the way FileMaker's own dialog groups the settings — Open,
Spelling, Text, Icon, Script Triggers — rather than in fm's key order. `minimumVersion` renders
`version` with `value` on hover, the same pattern `Get ( FileSize )` already uses. The startup
layout and each trigger's script render as links to their objects.

It deliberately gets **no row** in the catalog-counts table. An "Entries" count is meaningless for
one block, and the `field` row already shows what a non-conforming row costs in explanation.

### References

The block names other objects under documented keys with ids, so these are `named` references in
`refs.js` terms, not text-tokenised ones:

| Key | Reference |
|---|---|
| `layout` | the startup layout, when `switchToLayout` |
| `triggers[].script` | the script each file-level event runs |

Both enter `ui/analysis/refs.js` with `from: {kind: 'fileOptions'}`. A trigger's `field` key, when
present, is reported empty on the reference solution and is not treated as a reference until a file
is seen that sets it.

This retires a stated caveat. `ui/analysis/unreferenced.js:338` currently tells the reader:

> fm has no file-options read (toolkit gap file-options), so the file's startup layout and its
> opening and closing scripts are invisible: an object used only there is listed here.

That is now false and the note goes. On the reference solution no list changes — both `File Open`
and `noop` are referenced from elsewhere in ooe, checked — so the visible effect there is the
caveat's removal rather than a shorter list. On a solution whose startup layout is named only in
File Options, the list itself changes.

### Exports

File Options into the Markdown and JSON exporters. Not Mermaid: it has no graph shape.

### Errors

fm 0.7.0 has no such catalog and answers `unknown_catalog`. The panel renders the error and every
other panel on the page stays intact. The re-recorded fixture exercises only the success path, so
this needs a unit test against a synthesized error response.

## 2. Step-display catalog refresh

The pin bump already landed the new catalog. It is **not shippable without re-recording the
fixture**, and the failure is a regression rather than a gap in coverage.

Measured: steps-with-a-rendering-gap went 45 → 69 on the existing fixture. The cause is a shape
mismatch, confirmed by counting keys on both sides. The fixture, recorded at fm 0.7.0, carries
`opaque` 176 times, `editable` 176 and `reason` 177, and contains **zero** occurrences of
`exportOptions`, `importOptions`, `printOptions`, `pageSetup`, `sortOrder` or `findRequests`. The
new catalog references all six. So the catalog now describes step shapes the fixture cannot
contain, and the steps it describes best are the ones it renders worst.

The work: `npm run record` against fm 0.8.0-beta.0, then re-baseline the two hardcoded counts in
`tests/tabs/gaps.test.mjs` (the register's attribute total, 8502 → 8532, and the rendering-gap
figures). Expected direction after the re-record is **fewer** than 45 — Export Records and Page
Setup go from rendering nothing at all to rendering their options — and a count that goes the other
way means something other than fixture staleness is wrong and stops this task.

The build also restated five step entries: `opaque`, `editable` and `reason` are gone, and the bits
of the packed options word arrive as named booleans. The inspector reads none of those three keys
anywhere, checked, so this costs it nothing directly; it reaches the page through the catalog.

## 3. The four new steps

`MBS`, `Set Variable by Name`, `Replace Field Contents by Name`, `Set Script Triggers`. Rendering
comes free with the catalog. Their keys, read from fm's help rather than assumed:

| Step | Keys | Work |
|---|---|---|
| `Set Variable by Name` | `name`, `value`, `repetition` | analysis |
| `Replace Field Contents by Name` | `fieldName`, `replace`, `value`, `withDialog`, `specifyTargetField`, + 6 entry-option keys | analysis |
| `MBS` | `Function`, `P1`…`P9` | rendering only |
| `Set Script Triggers` | `on` | rendering only |

Two of them name an object by calculation rather than literally, and both belong in the same
unresolvable-name class the inspector already tracks:

- **`Set Variable by Name`** — `name` is a calculated variable name, so `ui/analysis/globals.js`
  must record a variable whose name is not statically known rather than silently miss it.
- **`Replace Field Contents by Name`** — `fieldName` is a calculated *field* name. This is the
  same class as the `GetField ( )` cases `unreferenced.js` already lists in its confidence reasons,
  and it joins that list. A step of this kind writes to a field the reference scan cannot name.

The other two need no analysis work, and the reason is worth recording so a later reader does not
go looking:

- **`Set Script Triggers`** takes one key, `on`. fm's help: "Disables or re-enables Script Triggers
  for the duration of this Script." It is a scoped on/off switch and names no script and no layout,
  so nothing enters `refs.js`. An earlier draft of this design claimed it named both; it does not.
- **`MBS`** is a plug-in step whose `Function` key carries the plug-in function's name as text and
  whose `P1`…`P9` carry its arguments. The name is a plug-in function's, not a solution object's,
  so it creates no reference edge. The step sits inside the still-open `plugin-call-sites` gap,
  which this build made sharper rather than smaller: fm now loads the installed plug-ins, so a
  formula calling one validates, and `references: true` still answers `[]` for it. The step
  renders; the inspector claims nothing about plug-in call sites and the existing caveat stands.

## 4. Inventory and register bookkeeping

`catalog-file-metadata` is now mostly closed, which is what fails
`tests/inventory-register.test.mjs:99`. That test asserts every mapped pair is still a real gap,
and the map at `docs/inventory-to-register.md:11` names five `file-options` attributes — "startup
layout", "login mode", "hide all toolbars", "minimum FileMaker version allowed to open the file",
"file script trigger event" — every one of which is now `reported: true`.

The gap id is repointed to the 13 rows that are still missing, and the affected rows in
`docs/saxml-inventory.md:14-18` are re-classified from `gap` to `covered`:

| Inventory row | Was | Becomes |
|---|---|---|
| `attr:'action'` — file ScriptTrigger action | gap | covered — `triggers[].event` |
| `attr:'name'` — startup layout and trigger script names | gap | covered — `layout`, `triggers[].script` |
| `attr:'type'` — Login type | gap | covered — `login.mode` |
| `attr:'keychain'` — SavePassword | gap | covered — `allowStoredCredentials` |
| `attr:'enable'` — HideToolbars / HideClientSharing / HideWebDirectSharing | gap | stays a gap for the two sharing flags only; `hideToolbars` is covered |

Each re-classification is checked against the register's own `reported` flag rather than against
this document, so the test is the arbiter.

## Out of scope, and what each would cost

Recorded so the next round does not have to rediscover them. All three overlap analyses the
inspector already computes offline from data it has in memory.

- **`validate:calculation` with `references: true`.** fm's own tokeniser, returning a formula's
  fields as `{kind, name, occurrence, id}` and its custom-function calls as `{kind, name, id}`.
  It would corroborate `refs.js`, including the one case `refs.js` documents itself as getting
  wrong — an occurrence or field name containing a space cannot be written in its token class.
  Opt-in, valid-branch only, and **one op per formula**, so it needs an on-demand path and a cost
  model the read-once page does not have today. Names nothing for variables, built-in functions,
  scripts or plug-in functions.
- **`variable:search`.** fm reports where a `$` or `$$` variable is set or read. Overlaps
  `globals.js`, which derives this by tokenising.
- **The eight catalog `*:search` ops and `text:search`.** fm's own "where is this used", against
  `refs.js`, which builds the whole index in memory. Cheap per use — one op per query — but adds a
  live-query path to a page that otherwise reads once and then answers offline.

## Testing

TDD, against the real block captured above rather than against the help text.

| Area | Test |
|---|---|
| Read plan | the list batch carries exactly one `read:fileOptions`, with no `detail` |
| Model | the block lands in `file.fileOptions`, not in a catalog slot, and is not mistaken for a list |
| Model | `unknown_catalog` lands in `error` and leaves the rest of the file intact |
| Solution tab | the panel renders every group, links the startup layout and each trigger script, and shows the error when the read failed |
| Refs | the startup layout and the six trigger scripts appear as `named` references from `fileOptions` |
| Unreferenced | the file-options confidence note is gone, and no other note changed |
| Exports | Markdown and JSON carry File Options; Mermaid does not |
| Steps | the four new step types render |
| Steps | `Set Variable by Name` is recorded as a non-literal variable name, and `Replace Field Contents by Name` as a non-literal field name |
| Register | the repointed `catalog-file-metadata` pairs are all still `reported: false` |
| Fixture | `meta.json` names build 29827611, and the rendering-gap count is below 45 |

Then the full gates: `npm test`, `INSPECTOR_LIVE=1 npm test`, and
`INSPECTOR_BROWSER=1 npm run test:browser`, all against fm 0.8.0-beta.0.

Every probe read-only, always: `read:*`, `evaluate:calculation`, `validate:calculation`, and
nothing else. The reference solution is read and never written.
